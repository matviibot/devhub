# Reframe DevHub Around Resuming Real Work

## Confirmed product constraints

The intended audience is **solo developers** managing roughly **3–20 projects**. The most frequent actions are **start or stop a project**, **open its local page/preview**, and, secondarily, **inspect logs**. DevHub should behave consistently across macOS, Windows, and Linux while using platform-native shortcut labels and conventions. It should also preserve a **small, bounded activity history across daemon restarts**—approximately seven days or the latest 200 meaningful events per project—without presenting historical observations as current state.

**DevHub should stop presenting itself as a project dashboard and become a resumable workspace switchboard:** a place where a developer can see what is waiting, recover the exact branch/worktree context, verify what is actually running, and take the next safe action. The stable object should remain the **project**, but the primary working object should be the **workspace**—a project-specific branch/worktree context that can contain an agent, services, readiness checks, and recent events. Home should therefore open on **Now**, not a gallery: first “Waiting for you,” then “Continue,” then “Recently changed.” The existing observation-first model, honest degraded states, and direct lifecycle controls are the product’s strongest ideas; the card grid, one-workspace-per-project compression, broad “attention” category, and page-local search obscure them. Research on interrupted programming supports chronological, concrete resumption cues, while strong developer tools consistently combine visible structure with contextual search and commands rather than forcing users to choose between navigation and a palette ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/evaluating-cues-for-resuming-interrupted-programming-tasks/); [VS Code workspaces](https://code.visualstudio.com/docs/editing/workspaces/workspaces); [Raycast search](https://manual.raycast.com/search-bar)). The redesign should make DevHub’s unique promise visible in every row: **what the developer or agent intended, what the daemon verified, what changed, and what to do next**.

## The current interface hides the product’s strongest idea

**Repository observation.** DevHub is already more than a launcher or process monitor. Its documented happy path registers a repository/worktree, maintains agent presence, reserves a port, announces a preview, verifies the listener, forwards termination signals, and leaves a done/failed handoff ([README](/Users/admin/dev/devhub/README.md:1)). Its model intentionally separates durable declarations from live observations, and it describes orphan processes and containers whose worktrees disappeared as the “highest-value thing devhub shows” ([shared model](/Users/admin/dev/devhub/packages/shared/src/index.ts:1)). Same-branch worktrees across repositories are grouped into a logical workspace, so the real mental model is already **Project → Workspace → Service/agent/check**, not simply Project → Repository. This is a differentiated trust model: agent intent can be declared, a port can be reserved, and a listener can be independently observed without conflating those claims.

**Repository observation.** The current presentation divides this coherent job across Projects, Active, Attention, Ports, and a project-detail route. Home is an auto-filling project-card grid; each card chooses one focus workspace by active agent, then live runtime, then array order, compressing the rest into counts ([Dashboard](/Users/admin/dev/devhub/packages/web/src/components/Dashboard.tsx:383)). Active separates agent work, runtime-only projects, and recent handoffs, but it does not order agent states by urgency or show the time of each handoff. Attention combines blocked readiness, daemon alerts, unattributed processes, and never-started containers even though those states differ in urgency and remedy ([Dashboard](/Users/admin/dev/devhub/packages/web/src/components/Dashboard.tsx:946)). Search exists only on Projects. Workspace tabs expose tab roles without the complete arrow-key, roving-tabindex, and tabpanel behavior expected of an accessible tabset. At narrow widths the UI hides state/context fields and moves all navigation into an overflow menu, while JavaScript and CSS use different breakpoints.

**Design diagnosis.** This architecture asks the user to decide which abstraction contains their next action before showing the action. It also makes a multi-worktree product look like a one-context-per-project product. The most coherent existing surface is project detail: it selects the workspace touched by the active agent, places task and runtime actions together, then progressively reveals readiness, runtime, exceptions, and sources. The redesign should generalize that logic upward rather than preserve the project-card home.

| Current assumption | Decision | Why |
|---|---|---|
| Projects are the primary durable objects. | **Preserve.** | Project remains the stable library, preference, and configuration boundary. |
| The Projects grid should therefore be home. | **Discard.** | Durable inventory is not the same as current priority; home should answer “what now?” |
| One project card can summarize one current context. | **Discard.** | Concurrent worktrees/agents make a single selected workspace misleading. |
| Starting a project means starting its primary checkout. | **Challenge.** | In an agent/worktree product the likely target is the current task workspace; bulk or preemptive effects must be explicit. |
| All “attention” belongs in one severity treatment. | **Discard.** | Waiting for a person, blocked setup, failed start, port collision, and cleanup debt require different ordering and actions. |
| Search and actions can remain page-local. | **Discard.** | Workspace switching, previews, logs, ports, and blockers are cross-cutting tasks. |
| Compact mode is desktop with less text. | **Discard.** | Side-panel width must preserve scope, blocker, and next action before ornamental identity. |
| Declared and observed state are different truths. | **Preserve and amplify.** | This is the clearest expression of DevHub’s product value. |
| Probes/disconnection must be shown as lost visibility, not health. | **Preserve.** | “Cannot observe” must never become “nothing is wrong.” |
| Every available datum deserves a card, badge, or permanent nav item. | **Discard.** | Relevance comes from urgency and task context, not feature inventory. |
| Generic dark developer-dashboard styling is enough. | **Discard.** | The interface should visually encode evidence and causality, not imitate hosting dashboards. |

Three plausible product frames clarify the decision. A **project launcher** is familiar and cheap to build, but it reduces DevHub to “open/start this repo” and handles concurrency badly. An **observability console** represents services, ports, and alerts accurately, but overweights machine inventory and implies a production-SRE audience. An **agent inbox** makes waiting and handoffs prominent, but fails when useful local work has no active agent. The recommended **resumable workspace switchboard** combines the best of all three: project is the stable place, workspace is the active context, agent/runtime state is evidence, and commands are actions. This resembles how VS Code persists workspace-specific state, how Codespaces resumes a branch-specific environment, and how Linear combines structured views, favorites, previews, and contextual commands ([VS Code](https://code.visualstudio.com/docs/editing/workspaces/workspaces); [GitHub Codespaces](https://docs.github.com/en/codespaces/developing-in-a-codespace/opening-an-existing-codespace?tool=webui); [Linear Peek](https://linear.app/docs/peek)). A service map or observability canvas can remain an optional mode for complex projects; it should not define home.

## “Now” organizes work by decisions, not entities

**Recommendation.** Use four visible global destinations: **Now**, **Projects**, **Attention**, and **Diagnostics**. Keep **Settings** separate and globally reachable. Now is the default and contains three short, ordered streams: “Waiting for you” (human decision or unblock required), “Running and recent” (active and recently used projects), and “Recently changed” (bounded handoffs or material runtime transitions). Projects is the durable, searchable library; workspace/worktree detail appears within a selected project instead of dominating home. Attention is an actionable exception queue ordered by user impact, not a red-badge archive. Diagnostics contains Ports, Unowned processes, probe health, and version/connection information. The omnibox and command palette are available everywhere, but visible navigation still teaches the product.

```text
Desktop home: Now
┌──────────────────────────────────────────────────────────────────────────────┐
│ DevHub     Search workspaces, services, commands…                 ⌘K   ● Live│
├──────────────┬───────────────────────────────────┬───────────────────────────┤
│ Now        3 │ Waiting for you                   │ Context preview           │
│ Workspaces   │ ┌───────────────────────────────┐ │ atlas / feat-auth         │
│ Attention  2 │ │ atlas · feat-auth            │ │ Agent intent              │
│ Diagnostics │ │ Blocked: database unavailable │ │ “Run login migration”     │
│              │ │ Last change 8m · Fix setup    │ │                           │
│ Favorites    │ └───────────────────────────────┘ │ Daemon observed           │
│ atlas        │                                   │ web :4317 running         │
│ docs         │ Continue                          │ db not listening           │
│              │ atlas / feat-auth   2 running     │                           │
│              │ docs / main         stopped      │ Open workspace   ↵         │
│              │                                   │ More actions      ⌘K       │
│              │ Recently changed                  │                           │
│              │ 10:42 API crashed after restart  │                           │
└──────────────┴───────────────────────────────────┴───────────────────────────┘
```

This is a comparison surface, not a grid of decorative cards. A **Project row** carries project, current workspace/branch when relevant, last meaningful event and time, verified runtime summary, and direct **Start/Stop**, **Open page**, and **Logs** actions. At the expected scale of 3–20 projects, this dense searchable list is faster to scan than a card grid. Selection updates a **Context preview** without navigation; `Enter` opens project detail and an action panel exposes alternatives. Chronological and concrete cues are well supported for interrupted programming: in one survey-and-study, automated cues doubled task-completion success relative to note-taking alone, and programmers strongly preferred chronological presentation ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/evaluating-cues-for-resuming-interrupted-programming-tasks/)). This evidence predates coding agents, so it supports the direction—not the precise number of rows or events.

```text
Project workspace: atlas / feat-auth
┌──────────────────────────────────────────────────────────────────────────────┐
│ ‹ Now   atlas / feat-auth ▾    Updated 18s ago   Open editor   Preview   ••• │
├────────────────────┬─────────────────────────────────┬───────────────────────┤
│ Workspaces         │ Task and next step              │ Evidence              │
│ ● feat-auth        │ Agent: Run login migration      │ Declared              │
│ ○ main             │ Blocked by database             │ db expected on :5432  │
│ ◐ test-cleanup     │ [Fix setup] [Show blocker log]  │                       │
│                    ├─────────────────────────────────┤ Observed              │
│                    │ Services                        │ db not listening      │
│                    │ web   Running  :4317  Preview   │ web listening :4317   │
│                    │ api   Crashed   —      Logs     │                       │
│                    │ db    Stopped   :5432  Start    │ Activity              │
│                    ├─────────────────────────────────┤ 10:42 api crashed      │
│                    │ Readiness   2 ready · 1 blocked │ 10:39 agent waiting    │
│                    │ Sources and configuration   ▾   │ 10:34 web verified     │
└────────────────────┴─────────────────────────────────┴───────────────────────┘
```

The workspace header is a persistent **scope bar**, because scope mistakes can stop sibling worktrees under a fixed-port policy. It must always name project + workspace and repeat any cross-workspace consequence before execution. The main column leads with the task/next step, then a compact service list, then readiness and configuration. The evidence rail makes DevHub’s signature distinction explicit: **Declared** (agent/config intent) versus **Observed** (daemon-verified machine truth), followed by a short causal timeline. Railway’s deployment markers over service metrics and Vercel’s separation of build from runtime logs illustrate why evidence should be correlated without being merged into one undifferentiated feed ([Railway metrics](https://docs.railway.com/observability/metrics); [Vercel logs](https://vercel.com/academy/vercel-foundations/logs)).

The core workflows follow this hierarchy. A **new user** lands on a one-screen explanation—“DevHub shows agent intent beside what your machine is actually running”—then adds or discovers a project and sees a real workspace row immediately; setup should not require dashboard customization. A **returning user** lands on Now, reads the last meaningful event, and presses “Resume workspace,” which restores the selected project/workspace and last useful panel when safe. A **multi-project user** scans aligned rows, pins a few favorites, filters with `/`, or invokes the global palette without losing visible structure. In a **degraded or offline state**, the current screen stays in place, every observed value carries “Last verified at …,” controls that require the daemon explain why they are unavailable, and the banner says “DevHub disconnected—showing the last verified state,” never “No services.” In **error recovery**, the receipt stays attached to the failed object: “API did not start. Port 4317 is used by docs / main. Stop that service and retry” with both actions available and scope named.

Responsive behavior should be based on available working width rather than “mobile” as a separate product. Above roughly 1100 CSS px, show navigation, list/main column, and preview/evidence rail. Between roughly 700–1099 px, turn the preview into a right drawer and keep a compact visible navigation strip. Below 700 px, use one column: a sticky but non-obscuring scope bar, textual blocker, primary action, then disclosures. Never hide status text merely to preserve project artwork. At a 320 CSS-pixel equivalent, all non-terminal UI must reflow without horizontal page scrolling; only logs/terminal content may scroll internally when two-dimensional content is essential ([WCAG 2.2 Reflow](https://www.w3.org/TR/WCAG22/#reflow)).

## A two-evidence visual system gives DevHub identity

**Design direction: the field instrument, not the SaaS cockpit.** Treat DevHub like a precise engineering notebook connected to live instruments: calm paper-like fields, aligned ruled rows, a narrow evidence rail, and small areas of high-signal color. Spend the visual boldness on the **Declared ↔ Observed** comparison. Avoid floating statistic cards, colored project initials, universal pills, gradient washes, and shadows that imply elevation without interaction. Use 1 px rules and 4 px corner radii only where containment or affordance requires them; large cards and nested rounded panels should disappear. Left-align nearly everything. Numbers, ports, paths, and times align on predictable columns so the interface can be scanned rather than decoded.

| Token | Value | Role |
|---|---:|---|
| Instrument paper | `#F3F5F7` | Default canvas; cool, quiet, and distinct from warm editorial templates. |
| Readout white | `#FFFFFF` | Selected rows, drawers, editable/control surfaces. |
| Carbon | `#17212B` | Primary text and strong boundaries. |
| Verified blue | `#005FCC` | Daemon-observed state, links, focus, and primary safe actions. |
| Intent violet | `#6B45A6` | Agent/config-declared intent; never used for verified state. |
| Exception red | `#B42318` | Blocked, failed, or destructive scope, always paired with icon and text. |

These are semantic anchors, not a complete production palette; derived backgrounds and dark-theme equivalents must be contrast-tested. Waiting/non-failure states should use Carbon with a clock or pause symbol rather than inventing another traffic-light color. Success should usually read “Running” or “Ready” with a verified icon; persistent green decoration would compete with exceptions. Light-first is intentional: DevHub is a local coordination instrument, and a cool high-legibility surface distinguishes it from generic near-black devtools. A dark theme can follow after the semantic system is stable, using the same evidence roles rather than literal color inversion.

Use a self-hosted variable build of **IBM Plex Sans** for interface text and **IBM Plex Mono** only for paths, branch refs, ports, commands, and logs, with `ui-sans-serif` and `ui-monospace` fallbacks. Ship the WOFF2 files with the app; the current Google Fonts and Material Symbols dependency makes an otherwise local control surface visually network-dependent ([font tokens](/Users/admin/dev/devhub/packages/web/src/ds/tokens/fonts.css:1)). Use sentence case, 14–15 px default text, 12–13 px metadata only where contrast remains strong, 20–24 px page/workspace titles, and line lengths under 80 characters. Icons should be local SVGs with a restrained 1.75 px stroke, never the only carrier of status or action. Keep an 8 px spacing base, 36–40 px dense desktop rows with at least 24 × 24 px pointer targets, and 44 px primary touch targets; WCAG 2.2 defines 24 × 24 px or sufficient spacing as the Level AA target-size floor ([WCAG 2.2 Target Size](https://www.w3.org/TR/WCAG22/#target-size-minimum)).

Motion should explain causality only. When a selected row updates the preview, crossfade changed content without moving the list. A start/stop action can replace the verb with a bounded progress state and then a receipt; do not pulse status dots or animate every row. Respect `prefers-reduced-motion` and provide static text equivalents ([W3C animation guidance](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions)). Snapshot refreshes should not reorder rows while the user is interacting; queue non-urgent resorting until focus leaves, while urgent blockers can appear in “Waiting for you” with an explicit announcement.

## Components turn status into an explanation and action

The component model should reflect user decisions rather than backend arrays. **ResumeRow** presents one workspace context; **ScopeBar** makes the action target persistent; **EvidencePair** aligns declared and observed claims; **NextAction** states one recommended verb; **ServiceLine** shows lifecycle, listener, launcher availability, and inline action; **ActivityThread** groups events causally; **ContextPreview** supports peek-before-navigate; **ActionReceipt** reports pending/succeeded/failed state beside the object; and **CapabilityBanner** distinguishes disconnected, Docker unavailable, `lsof` unavailable, and version-skew states. **WorkspaceSwitcher** should scale beyond horizontal tabs, support typeahead and complete listbox/tab keyboard semantics, and show concurrent agent/runtime state. **ScopeConfirm** is reserved for actions with destructive or sibling-workspace consequences.

Status must be compositional, not one colored badge. Each rendered status should answer four fields: **lifecycle** (“Starting,” “Running,” “Stopped,” “Crashed”); **evidence** (“Agent reported,” “Daemon verified,” “Last verified 10:42”); **impact** (“Waiting for you,” “Blocks preview,” “Cleanup recommended”); and **action** (“Show logs,” “Fix setup,” “Retry”). A service can therefore read: “API — Crashed · daemon verified 18s ago · blocks preview · Show logs.” An intent mismatch can read: “Database expected on `:5432`; no listener observed.” This preserves epistemic honesty and remains meaningful without color.

Interface copy should name the event, scope, and consequence. Prefer “Resume `atlas / feat-auth`” to “Open”; “Start web in `feat-auth`” to “Run”; “Stop `docs / main` first, then start this service” to “Port conflict”; “Docker observation unavailable—containers are hidden, not stopped” to “Docker error”; and “DevHub disconnected—showing state last verified at 10:42” to “Offline.” Empty states should be invitations with a reason: “Nothing needs your decision. Continue recent work below”; “No workspaces yet. Add a project or run `agent run` from a repository”; “No unowned processes found in the last scan.” Errors should preserve entered values, identify the failed field/action, and offer a repair path, consistent with GOV.UK’s validated recovery pattern ([GOV.UK validation errors](https://design-system.service.gov.uk/patterns/validation/)).

The command surface should be **dual-channel**. `Cmd/Ctrl+K` opens the global palette; `/` focuses filtering for the current collection when typing focus is not active. With an empty query, show recent workspaces, waiting items, and frequent safe actions. Results use verb-first labels and expose scope: “Resume atlas / feat-auth,” “Show API crash logs — atlas / feat-auth,” “Start web — docs / main.” Visible chips or prefixes narrow to Workspaces, Services, Commands, Events, and Ports. Arrow keys traverse, `Enter` opens/runs, `Escape` closes without committing, and a secondary action panel exposes alternatives. Every core action also remains visible in the interface, and shortcut hints appear beside controls and results. This follows established command-palette patterns while preserving recognition and discoverability ([VS Code interface](https://code.visualstudio.com/docs/editing/getting-started/userinterface); [Warp command palette](https://docs.warp.dev/terminal/command-palette); [WAI-ARIA combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/)).

WCAG 2.2 AA should be a release floor, with stronger focus appearance and reduced-motion behavior adopted as product standards. All functionality must work by keyboard; focus must remain visible and unobscured; overlays restore focus to their trigger; status changes use polite live regions without announcing streaming log lines; normal text reaches 4.5:1 contrast and essential controls/state boundaries 3:1; no state relies on color alone; and interface structure remains programmatically determinable ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)). Every release should include keyboard-only flows, 200%/400% zoom, 320 CSS-pixel reflow, reduced motion, forced colors, automated scanning, and manual screen-reader smoke tests for navigation, dynamic status, drawers/dialogs, and the palette. Terminal/log accessibility needs separate evaluation and a plain-text alternative if the emulator cannot expose useful content.

## Ship the reframing in three testable steps

**Now — repair the information hierarchy without requiring new daemon history.** Replace the project grid default with a snapshot-derived Now view containing “Waiting for you” and “Continue”; keep Workspaces as the library; order exceptions by impact; add explicit timestamps/freshness; make search global; preserve scope in all actions; and remove external font/icon dependencies. Split the approximately 2,300-line [Dashboard](/Users/admin/dev/devhub/packages/web/src/components/Dashboard.tsx:1) into route/domain components and break the roughly 2,000-line [stylesheet](/Users/admin/dev/devhub/packages/web/src/styles.css:1) into semantic tokens and feature styles. Delete unused legacy `Rail`, `CompactBar`, and `ProjectPane` paths after verification. Add component, keyboard, action-state, and responsive tests before large visual changes. Likely affected areas include `Dashboard.tsx`, `App.tsx`, `styles.css`, `ds/tokens`, `useBreakpoint.ts`, and UI preferences in the shared package. The principal risk is changing hierarchy while snapshot order remains unstable; stable semantic keys and focus-preserving sort behavior are required.

**Next — make commands and evidence first-class.** Add the contextual command palette, result preview, scalable workspace switcher, evidence rail, causal grouping of current snapshot events, and one consistent action-receipt system. Extend preferences to remember last workspace/view, favorites, and safe UI state using existing semantic keys. Normalize action metadata so every start/stop/restart can describe target, reversibility, fixed-port preemption, and launchability before execution. Likely affected areas include the web component tree, `useDevhub.ts`, shared action/view types, WebSocket command contracts, and accessibility test infrastructure. The major risks are stale search results across snapshot updates, focus loss in a rapidly changing list, shortcut collisions, and accidental treatment of agent-declared state as verified state.

**Later — add trustworthy chronology and optional complexity.** Introduce the confirmed bounded event model after defining provenance, ordering, and restart behavior: retain approximately seven days or the latest 200 meaningful events per project. The current short-lived handoff lease cannot support this durable activity timeline by itself. Then add activity filters, resumption history, and an optional service topology for genuinely multi-service projects. Consider adaptive defaults or user-chosen home only after telemetry shows stable cohorts, as Linear allows a configurable default view ([Linear preferences](https://linear.app/docs/account-preferences)). The main product risk is undermining the observation-first philosophy by persisting stale “truth”; durable events must be immutable historical claims (“observed at 10:42”), never cached current state.

Success should be measured as task outcomes, not aesthetic approval. Establish a baseline, then test these targets: all formative participants can identify and reopen the most recent workspace without entering an unrelated detail view; at least 90% of representative attempts identify a seeded blocker and its prescribed next action without relying on color; median wrong turns and time-to-resume improve versus the current Projects home; users can complete resume, inspect logs, start/restart/stop, and return from overlays by keyboard alone; destructive-scope errors trend toward zero; and no release regresses AA contrast, targets, focus, reflow, or status announcements. Instrument which Now rows/actions are used, which disclosures reopen repeatedly, palette success/abandonment, action failures, and reconnect recovery—but do not infer that hidden features are unneeded without observing discoverability.

Validation should begin with five to eight representative developers across three profiles: a single-project agent user, a multi-project/worktree maintainer, and someone supervising several simultaneous agents. Run comparable tasks on the existing UI and a low-fidelity clickable prototype: resume interrupted work, find what waits for input, resolve a port collision, inspect a failed start, and understand a probe outage. Follow with a one-week dogfood study that records interaction events and brief confidence ratings, then refine hierarchy before committing to persistent event history or a service canvas. The card-versus-row choice, number of recent contexts, “project/workspace” vocabulary, and default primary action should remain falsifiable design hypotheses, not doctrine.

## Conclusion

DevHub’s opportunity is not to become a prettier dashboard. It is to make a difficult local-development truth legible: agents declare intent, machines reveal observations, and developers need to resume the right context when those two diverge. Organizing the product around Now → workspace → evidence/action turns that model into a daily workflow while keeping deep diagnostics available without letting them dominate.

The central product choices are now resolved: DevHub is for solo developers managing roughly 3–20 projects; start/stop and opening the local page are the primary actions, with logs secondary; bounded history persists across daemon restarts; and the experience must remain equally capable across desktop platforms. The next unresolved design questions should be tested in a prototype rather than decided abstractly: whether a running project opens its page immediately after Start, whether stopping requires confirmation when an agent is active, and how DevHub chooses the launch target when a project has multiple runnable workspaces.
